## Authorization source audit

The G3 `ExecutionBoundaryRequest` includes UUID `admission_ref` and `budget_ref`. New server-owned `DownloadExecutionAdmissionModel` and `DownloadExecutionBudgetModel` tables now provide the persisted binding and shared byte-budget representation, with a transaction repository that resolves both references, checks Task/owner/caller/protocol/expiry/policy linkage, consumes once with an execution epoch, and conditionally reserves bytes. The models are not yet created by `DatasetImportService` or consumed by a Supervisor, so this is code and isolated-test evidence only. `DatasetIngestionModel` remains the existing Prepare authority containing owner/project, normalized request/source snapshot, `max_bytes`, confirmation ID, Task IDs, and lifecycle state; its processed mode is the first intended source. Raw mode can create multiple Tasks and remains outside this binding. Exact source findings are recorded in [`admission-source-audit.md`](../../evidence/g3-e2-20261018/admission-source-audit.md).

This is a separate implementation blocker from the missing Linux runtime. Do not trust caller-supplied references or start an execution until the new admission rows are issued from the existing processed-import Prepare/Approval record and atomically bound to the exact Task, normalized request/source digest, owner/project, HTTP policy, shared budget, expiry, caller/environment, and trusted execution epoch. The repository is ready for that wiring, but the lifecycle and Supervisor server are not yet connected. Current code remains fail-closed.

## Implemented contract

`ExecutionBoundaryObservation` requires measured inode peak usage and distinguishes task-admitted RX from observed and dropped RX; the three values must reconcile, while only admitted RX is compared with the task budget. It binds task/scope/execution/epoch and policy and records start/stop time, cgroup population, egress revocation, quota enforcement, cleanup completion, and disk/inode measurements. Signed Ed25519 receipts additionally bind task attempt, execution, epoch, policy, environment, binary SHA-256, artifact-manifest SHA-256, supervisor identity, expiry, and nonce. The publication predicate rejects nonzero exit, live/populated cgroups, unrevoked egress, missing hard quota or cleanup evidence, and any measured task budget overrun.

Nonce consumption now has a SQLAlchemy repository and dedicated table/migration with a unique `(supervisor_id, nonce)` constraint. Receipt verification uses the caller's `AsyncSession` without committing. The Worker direct-link HTTP registration path computes a manifest hash from actual output files, validates the signed task/attempt/execution/scope/epoch/policy/environment/binary receipt against the pinned supervisor key, consumes its nonce, and only then registers files through `FileRegistry` in the caller's transaction. SQLite tests cover signed registration, replay rejection, rollback, expiry cleanup, receipt identity mismatch and RX counter consistency. This is isolated publication-gate evidence; no concrete Supervisor currently creates or supplies `_download_execution`, the migration has not been applied to a real database, and PostgreSQL concurrency is unverified. There is still no OS-side Supervisor implementation, enforced network boundary, hard byte/inode quota enforcer, or task stop/cgroup integration. HTTP/HTTPS execution fails closed before launching the downloader when no trusted execution adapter is available. G3 acceptance remains blocked.

A Worker-side `MutualTLSExecutionAdapter` now implements the `TrustedExecutionAdapter` client contract for `start`, `observe`, `renew`, `stop`, and `evidence`. The evidence read requires the original `ExecutionBoundaryRequest`; it checks supervisor, Task, scope, attempt, execution, epoch, policy, environment, binary, and observation bindings against that request before returning a signed publication context. Cryptographic receipt verification and artifact-manifest matching remain the publication gate's responsibility. The client requires an HTTPS endpoint, configured CA and client certificate/key outside tests, disables proxy environment inheritance and redirects, uses bounded timeouts, requests identity encoding, rejects compressed responses, and incrementally caps raw response bodies at 64 KiB. It performs no automatic retry. Its test-only `MockTransport` is rejected outside `test`/`acceptance`. This is only the authenticated client: no matching Supervisor server or OS enforcement process exists, the client is not wired into Worker task startup/stop, and no adapter response can currently be produced by a deployed service. Configuration names are documented in `.env.example`; keeping them unset does not alter existing fail-closed behavior.

## Required before runtime acceptance

First extend the durable processed-import Prepare/Approval binding with approval consumption, same-Task execution fencing, and a restart-safe shared byte budget. Then implement and review the matching Supervisor server and OS runtime that enforce destination policy and hard receive/inode limits at the host boundary, terminate the entire process group/cgroup, record measured usage, and issue the signed execution context to the Worker. Wire the mTLS client into the existing Task lifecycle only after the server and its independent authorization checks exist. The current host cannot satisfy the required capability and writable-cgroup prerequisites; an authorized dedicated Linux host with the reviewed kernel/network/quota facilities is required. Apply migrations and prove PostgreSQL concurrency there. Then run the nine HTTP boundary scenarios in a disposable authorized environment and retain supervisor, network, quota, stop, receipt, and publication evidence. Keep all release switches closed until that evidence is reviewed.

The operator preflight must verify a delegated cgroup v2 subtree with writable task cgroups and `cgroup.kill`, namespace creation under the intended supervisor identity, an XFS (or reviewed equivalent) test volume with block and inode hard quotas actually enabled, and an egress hook whose shared atomic RX accounting semantics have been validated on the target kernel. Tool presence, namespace handles, `bpftool feature` output, or mount-option text alone do not prove those controls. The controlled HTTP origin, dedicated database/role, Redis, broker, queue, worker and cleanup owner must be identified before any start; missing prerequisites mean no start and no test skip promotion.
