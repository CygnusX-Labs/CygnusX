### 题 2. fetchAll 竞态分析

**结论：完全没有竞态防护——无 abort、无去抖、无版本号/请求序号；useApi 的 loading 也会被并发调用打穿。**

证据：

1. `useApi.execute`（`frontend/src/composables/useApi.ts:31-49`）：
   ```ts
   async function execute() {
     loading.value = true
     error.value = ''
     try { const result = await fetcher() ... }
     finally { loading.value = false }
   }
   ```
   两次并发 execute 时：A 开始（loading=true）→ B 开始（loading=true）→ A 结束（loading=**false**，但 B 还在飞）→ B 结束。中间窗口 loading 状态失真（NSpin 闪烁消失又出现）。
2. fetchAll 的 fetcher（FilesView:67-83）直接对 5 个 ref 赋值，**后完成的请求覆盖先完成的**。没有任何 AbortController。
3. 触发 fetchAll 的路径共 8 处：syncFiles finally（:315）、删除后（:383）、移动后（:418）、`watch(completedSeq)`（:446-448）、目录树 `@refresh-files`（:499、:857）、错误重试按钮（:633）、「清理缓存」（:811、:904）。
4. **最坏交叉**：`onMounted → syncFiles(true)` 的 finally 会 fetchAll，而上传完成也触发 `watch(completedSeq) → fetchAll`。若用户在进入页面后立刻有上传完成（如悬浮球里有在途任务切页过来），两个 fetchAll 并发，返回顺序不定，`allFiles` 可能被较旧的响应覆盖（`GET /files` 是全量拉取，谁后到谁生效，与谁发起晚无关）。
5. `watch(completedSeq)` 无去抖：批量上传 N 个文件完成 → N 次 fetchAll 风暴（每个文件 merge 完成自增一次，`stores/upload.ts:42-44`）。

### 题 5. 后端错误统一格式 + 前端拦截器

后端（`main.py:414-422`）：
```python
@app.exception_handler(CygnusXError)
async def cygnusx_error_handler(request, exc):
    content = {"detail": exc.detail}
    if exc.code: content["code"] = exc.code
    return JSONResponse(status_code=exc.status_code, content=content)
```
- body 恒为 `{ detail: string, code?: string }`；**code 无枚举注册表**，仅按异常类映射 status：`NotFoundError`→404、`AuthorizationError`→403、`ValidationError`→422、`QuotaExceededError`→403（core/exceptions.py:16-76）、`BusinessError`→400、`RateLimitError`→429。
- 特例：`MODULE_LOCKED`（模块锁）走 403 + `code='MODULE_LOCKED'`。
- 请求参数校验失败：`RequestValidationError` 单独 handler（main.py:425+），422 带字段错误数组；未捕获异常兜底 500。

前端 `apiClient`（`frontend/src/api/client.ts:82-122`）响应拦截器只处理三件事：
1. 401 → 尝试 refresh token + 重放一次（:88-112）；
2. 403 + `code==='MODULE_LOCKED'` → 离散 dialog 弹模块未开通（:114-118）；
3. **其余一切错误原样 reject，不做任何 toast**——错误提示完全依赖各调用方自己 catch。

含义：任何组件漏 catch 就会变成 unhandled rejection（静默失败）；而 `e.response.data.detail` 是约定的错误文案提取路径（FilesView 删除/移动遵循，下载未遵循，见题 1）。

### 题 6. `GET /files` 查询参数确切语义（files.py:175-193 + file_service.py:353-380/487-543）

| 参数 | 语义 | 边界 |
|---|---|---|
| `?directory=` | **list 模式按目录直查**（`_files.list_visible(user_id, status='active', directory=...)`）；非递归，返回该目录直接子文件 | 传空串 = 根目录；不传 = 不过滤（返回全部可见文件，含团队）；**但前端从未传任何参数**（FilesView:69） |

## 三、上传边界与团队空间

### 题 7. 上传边界行为

**同名文件**：不报错、不覆盖——**自动加 8 位 hex 去重后缀**。`upload_service.py:215-217`：
```python
final_path = inbox_subdir / session.file_name
if await self._backend.exists(final_rel):
    final_path = _append_dedupe_suffix(final_path, uuid.uuid4().hex[:8])
```
原文件名保留在 `original_name`，物理文件名变为 `{stem}_{hex8}{ext}`。前端 merge 后不检查冲突，直接 toast 完成——**用户不知道文件被改名落盘**（列表里显示的仍是 original_name，只有 JBrowse 直链用的 path 暴露真实名）。

**秒传命中条件**（`find_completed`，file_repository.py:258-266 + upload_service.py:101-112）：`user_id + file_name + total_size` 三元组匹配且已有 status='completed' 的会话 → 直接返回 `completed=True`。
- ⚠️ **冲突风险 1**：**与 file_md5 无关**——同名同大小但内容不同的文件会被误判秒传，跳过上传直接"完成"，但 `file_id=None`（:109），前端 useChunkUpload.ts:143-149 拿到的 mergeResp 是**前端伪造的**（file_id=''、checksum=采样 MD5），页面上不会出现新文件记录（因为后端根本没建）。用户以为传完了，实际列表里只有旧文件。
- ⚠️ **冲突风险 2**：秒传仅比对**会话表**，若用户删了文件但 upload_sessions 里 completed 记录还在，秒传返回成功但 file_records 已无对应文件。

**配额拦截层**：init_upload 第一道（upload_service.py:95-99，`QuotaExceededError`→403，detail 含已用/配额/本次需字样）；presigned 路径第二道（file_service.py:647-649，ValidationError）；merge 后 `add_used_storage` 落账（:251）。**前端看到什么**：useChunkUpload.ts:252-255 把 `e.response.data.detail` 写进 `item.error`，ChunkUploader 列表项展示红 tag「失败」+ 错误文案——有提示但**不在上传按钮处，需要用户打开弹窗才能看到**。另注意：配额校验只看 `used + total_size`，**不扣除同次会话重复 init**（暂停后 resume 重新 init 不会重复计费，因为 session 复用；但取消后重新上传同名文件走新 session，init 时 used_storage 还没加 merge 的量——多次大文件同时 init 可超卖配额，merge 落账时才穿底，无回滚拦截）。

**多任务并发上限**：**前端无全局上限**。`stores/upload.ts:93-109` 的 `addFile` 对每个文件立即 `controller.run()`——选 10 个文件 = 10 个任务并发，每个任务内部再 3 并发分片 = 最多 30 个在途 chunk 请求（useChunkUpload.ts:18 `CONCURRENCY=3`，:219）。后端 rate limit 已对上传路径豁免（useChunkUpload.ts:186 注释），429 兜底重试存在。浏览器对同 host HTTP/1.1 有 6 连接上限（经 nginx :8888），实际会排队但前端 speed 计算会失真。

**`uploaded_chunks` 断点失效**：
- Celery Beat `cleanup_expired` 每日清理 `status in (pending, uploading) 且 updated_at < file_upload_session_timeout_hours(默认24h)` 的会话 + `.tmp` 分片（celery_app/tasks/storage.py:81-93）。→ 暂停超 24h 后 resume：init 重新建 session，uploaded_chunks 空，从头传（旧 tmp 已删，不算错误）。
- merge 失败置 status='failed'（upload_service.py:272-277）；failed 会话 init 不会复用（find_completed 只找 completed），同样从头传。
- **merge 已 completed 的会话**：再 merge 报 ValidationError「上传会话已合并完成」（:180-181）——前端只在正常流程触发一次，无影响。

| 删除 | 个人 owner；团队 **owner 任意删**；**writer 仅可删自己上传的**（`file.user_id == actor_user_id`） | **前端只判 role==='owner'，writer 一律不显示删除按钮** | ❌ **前后端不一致**：后端允许 writer 删除自己上传的团队文件，前端把按钮藏了——功能存在但不可达（严格说是前端比后端更严，无越权风险，但功能阉割） |

另注意：前端 `canWrite`/`canDelete` 判定基于 `/teams` 返回的 role，而 `activeSpace==='team'` 时显示的文件是**前端过滤** `owner_scope==='team' && team_id===selectedTeamId`（:114-120），若用户被移出团队但列表未刷新，按钮仍按旧 role 显示——后端 `_require_*_access` 会兜底 403，安全无虞但体验是"点了删除才报错"。

### 题 17. 「近期活跃轨迹」推导逻辑

RecentActivitiesWidget.vue:35-53（完整）：
```ts

  const uploads: Activity[] = props.files.map((f) => ({
    type: 'upload', title: `上传了 ${f.original_name}`,
```
