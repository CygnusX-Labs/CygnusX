# 数据管理前端优化方案

> 版本：v2.0 · 2026-10-03（整合《数据管理前端补充调查报告》18 题结论后修订，替代 v1.0）
> 输入：`数据管理前端现状调查.md` + 页面截图 + `数据管理前端补充调查报告.md`
> 目标读者：前端 owner、后端配合人、技术负责人、产品决策人

## 0. v1 → v2 变更摘要

v1 的三个最大盲区（零运行时证据、性能未实测、错误处理未审）中，**错误处理与契约细节已通过补充调查补齐**；性能仍需实测（报告 R4/R7）；实测缺陷清单收敛为 10 项（附录 A）。v2 的实质性变化：

1. **P0 不再是"待验证"，有了代码级实锤缺陷清单**（§2-A），其中「秒传误判」是数据正确性问题，列为最高优先。
2. **补充调查报告推翻/修正了 v1 的三处判断**：① 错误处理并非全无——0 处无 catch，问题是"吞 detail"和静默同步；② 桌面/移动模板重复约 95 行、无逻辑分叉，合并改造面比预想小；③ Monaco 无 XSS、blob URL 无泄漏，安全面比预想干净。
3. 新增 **后端确定性缺陷**（秒传、配额超卖），优化范围从纯前端扩为前后端协同。
4. API 层进入可定稿状态：响应 schema 与错误格式已齐（§4 Phase 1 附接口草案）。

## 2. 补充调查的关键新发现

### A. 确定性缺陷（代码级证据充分，无需实测即可立项）

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| **A1** | **秒传误判（数据正确性）**：命中条件是 `user_id + file_name + total_size` 三元组，**与内容 MD5 无关**；命中后 `file_id=None`，前端 mergeResp 是伪造的（file_id=''），后端不建 file_records | 补充报告题 7（file_repository.py:258-266、useChunkUpload.ts:143-149） | 同名同大小不同内容的文件"秒传成功"但列表里根本不存在——**用户丢失数据且无任何提示**；删过文件但旧会话还在时同样假成功 |
| **A2** | **fetchAll 零竞态防护**：无 abort/去抖/版本号；`useApi.execute` 并发时 loading 失真；`watch(completedSeq)` 无去抖，批量上传 N 个文件 = N 次全量 fetchAll 风暴；两个 fetchAll 并发时旧响应可覆盖新响应 | 题 2（useApi.ts:31-49、FilesView:446-448、stores/upload.ts:42-44） | 列表闪烁、数据错显、无谓的服务端压力 |
| **A3** | **进页静默同步失败无感知**：`syncFiles(true)` 吞掉错误，finally 仍 fetchAll → 用户看到未对账的陈旧列表且不知道 | 题 1 #5（FilesView:300-317、:456） | 磁盘与 DB 不一致时用户被蒙在鼓里 |
| **A4** | **下载失败统一文案吞 detail**：配额 403 / 404 / 团队无权限全是"下载失败，请稍后重试" | 题 1 #11b（FilesView:358-370） | 用户无法区分"重试有用"和"重试没用" |
| **A5** | **统计卡闪零 + 口径混乱**：OverviewStats 在 NSpin 外，首屏显示 0/0/0/0%；且四张卡四种口径——Files=个人+团队混合总数、Samples=纯个人、**Projects=顶层自建目录数（与项目模块毫无关系）**、右栏文件夹数=全量含系统目录 | 题 3、题 16 | 首屏观感差；"Projects 5"是对用户的直接误导 |
| **A6** | **预览白名单不含生信格式**：fastq/fasta/vcf/gff 等最常见的文件类型全部落入"不支持"分支；与 chat-upload 白名单、JbrowseFileDrawer 三处口径不一 | 题 10 | 数据管理页对本平台核心文件类型不支持预览 |
| **A7** | **团队 writer 删除功能存在但不可达**：后端允许 writer 删自己上传的团队文件，前端按 role==='owner' 藏了按钮 | 题 8 | 功能阉割（前端更严，无越权风险）；需产品定夺（R10） |
| **A8** | **「清理缓存」名不副实**：实为重新 fetchAll，无任何清理动作也无提示 | 题 1 #19 | 欺骗性文案 |
| **A9** | **同名上传被静默改名**：后端自动加 8 位 hex 后缀，前端不提示 | 题 7（upload_service.py:215-217） | 用户通过 JBrowse 直链才发现物理文件名对不上 |
| **A10** | **上传并发无全局上限**：10 文件 = 10 任务 × 3 分片 = 最多 30 个在途请求，浏览器 6 连接排队导致速度显示失真 | 题 7 | 弱网/大文件场景进度不可信 |
| **A11** | **配额超卖窗口**：并发 init 各自校验 `used + size` 不扣除同批其他会话，merge 落账时才穿底，无回滚 | 题 7 | 多任务并发时可突破配额 |
| **A12** | **目录树无 empty/error 态**；文件列表"error 但有旧数据"时无任何提示 | 题 1、题 3 | 数据过期不可知 |

### B. 推翻 v1 担忧项（无需再投入）

- 所有直接 API 调用都有 catch（仅静默同步 1 处无提示）；无 unhandled rejection 面。
- FilePreviewModal：blob URL 三条路径都 revoke，无泄漏；Monaco 纯文本渲染，无 XSS。
- 右键菜单定位无注入面，仅视口边缘可能溢出（R6 实测）。
- 桌面/移动模板重复约 95 行、纯复制无逻辑分叉，合并为 3 个子组件 + `isDrawer` 一处分支即可，改造面小。

### C. 仍需运行时验证的 10 项

见附录 A（R1–R10）。其中对优先级影响最大的是 **R4**（大目录首屏实测）和 **R3**（Celery 清理 worker 是否在跑）。

## 4. 优化方案（分阶段 + 验收标准）

### Phase 0｜运行时验证（0.5–1 天）

只做附录 A 的 R1–R10，重点是 R3（查部署环境 Celery beat 是否在跑、`file_upload_session_timeout_hours` 实际值）、R4（造 5000 文件测首屏）、R7（Monaco 首次预览弱网加载）。其余 7 项可并行随手验。

验收：R1–R10 每格有结论；R4/R7 数据决定 Phase 3/5 的性能项深浅。

### Phase 1｜修复 P0 确定性缺陷（2–3 天，前后端协同，可独立上线）

| 项 | 修法 | 端 |
|---|---|---|
| A1 秒传 | 命中条件加入内容 MD5（秒传采样 MD5 已算好，init 入参带上即可）；或后端返回 completed 时要求 `file_id` 非空，为空则视为未命中继续传。**合并响应禁止前端伪造**（useChunkUpload 拿不到真 file_id 就报错重试） | 前后端 |
| A2 竞态 | upload store 的 completedSeq 改为去抖合并信号（如 300ms 窗口）；files store 的 fetch 携带递增序号，仅最后一次响应生效；`useApi` 并发计数修 loading 失真 | 前端 |
| A3 静默同步 | silent 失败时写入 store 的 `syncError` 状态，在统计带下方给一次性可关闭提示条（"对账失败，显示的数据可能不是最新"） | 前端 |
| A5 口径 | Projects 卡改名为「根目录」或「我的目录」并改口径说明；四卡口径在卡片加 tooltip 注明统计范围；闪零 → 首屏未返回前显示骨架屏 | 前端（后端聚合端点见 Phase 6） |

验收：构造同名同大小不同内容文件上传 → 必须真实落盘或明确报错；批量上传 10 文件 → 网络面板 fetchAll 请求 ≤2 次；断网同步 → 页面有提示条。

### Phase 2｜API 层 + 状态层（2–3 天）

**`src/api/files.ts` 接口草案**（schema 已按补充报告题 4 定稿）：

```ts
// 响应类型（与 application/schemas/file.py 对齐）
interface DataFileDTO { id: string; original_name: string; size: number; file_type: string;
  status: string; checksum: string | null; directory: string; path: string; source: string;
  owner_scope: string; team_id: string | null; created_at: string; modified_at: string }
interface DirectoryDTO { id: string; path: string; name: string; parent_path: string | null;
  is_system: boolean; created_at: string; modified_at: string }
interface FileListResponse { items: DataFileDTO[]; directories: DirectorySearchDTO[]; total: number }
interface QuotaResponse { used: number; total: number; percent: number }
// 错误约定：body 恒为 { detail: string, code?: string }（CygnusXError 统一 handler），
// 前端按 e.response.data.detail 取文案，code 仅 'MODULE_LOCKED' 有特殊语义

// 接口
listFiles(params?: { directory?: string; q?: string; source?: string; limit?: number }): Promise<FileListResponse>
listDirectories(): Promise<DirectoryDTO[]>            // 裸数组
getQuota(): Promise<QuotaResponse>
listSamples(): Promise<{ items: SampleDTO[]; total: number }>
moveFile(id: string, directory: string): Promise<...>
deleteFile(id: string): Promise<void>
createDirectory(path: string): Promise<...>
deleteDirectory(path: string): Promise<void>
syncFiles(): Promise<SyncResult>
previewByPath(path: string, maxLines?: number): Promise<{ path; truncated; total_size; lines: string[]; message?: string }>
getUploadInit/Chunk/Merge/...                          // 上传协议保持原样，仅迁文件位置
```

**`src/stores/files.ts`**：持有 files/directories/quota/samples/teams/activeSpace/currentDirectory/searchQuery/viewMode；单一数据源；`refreshCurrent` 带序号防竞态（Phase 1 的修法在此落地为长期结构）。DirectoryTree 与右栏全部改消费 store。

验收：组件内零 `apiClient`；directories 全局一份；切目录只发 1 个请求。

### Phase 3｜组件拆分 + 错误处理统一（3–5 天）

- 拆 `SpaceSwitcher` / `TreePanel` / `FilesToolbar` / `FileBreadcrumb` / `FileTable` / `FileGrid` / `DetailPanelGroup`（含移动抽屉合一，`isDrawer` 一处分支）；FilesView < 300 行。
- 错误处理：API 层统一封装 toast + `detail` 原文（修 A4），特殊 code 分流；每块数据区补三态（修 A12）。
- DirectoryTree 新建弹窗改受控表单（去 getElementById）；右键菜单定位加边界翻转。

验收：行为快照测试过 CI；断点三档下无重复模板。

### Phase 4｜服务端过滤与交互（2–3 天，深浅由 R4 决定）

- 切目录走 `?directory=`（语义已确认：非递归直查，空串=根）；搜索防抖走 `?q=`（默认 limit 50、封顶 200，UI 需提示"仅显示前 N 条"）。
- `allFiles` 退出列表渲染路径，仅留统计用（或迁后端聚合）。
- 视 Phase 0 结论补多选/批量操作、面包屑。
- A10：上传并发上限（建议全局 3 任务，排队制）。

### Phase 5｜产品完整性决策（0.5 天决策 + 分散实现）

| 项 | 建议 | 备注 |
|---|---|---|
| 假功能（重命名/SRA/GEO/URL/管理存储/帮助） | 按 v1 决策矩阵执行（重命名实现，SRA/GEO 撤按钮，其余撤或改） | SRA/GEO 与 `/downloads` 重复已确认 |
| A6 预览白名单 | 补 fastq/fasta/vcf/gff/bed/sam/bam(走 JBrowse) 等生信格式；三处白名单合一为单一配置源 | 改用 `/files/preview`（注意入参是 **path 不是 id**），去掉整文件 blob 下载与 25MB 上限 |
| A7 writer 删除 | **产品决策**（R10）：建议对齐后端放开按钮 | 前端更严无安全风险的阉割 |
| 伪活跃轨迹 | 升级为真实事件流：audit_logs 已记本域全部写操作（资源类型 resource_type='files'），缺用户级查询端点（Phase 6）；上线前临时改名「最近上传」并注明口径 | 下载/预览无审计是已知边界 |
| 目录命名（N1） | `raw_data` 是系统目录，截图里 `raw`/`raw-data` 是用户自建——治理方案 = 目录改名能力（依赖 Phase 6 rename 端点）+ 新用户默认目录文档化 | |
| Monaco | 改 `defineAsyncComponent` 延迟到弹窗打开（R7 数据定是否必须） | |

### Phase 6｜后端配合项（按优先级）

1. **秒传修复**（A1，与 Phase 1 同步）：init 入参加 MD5，命中校验加内容比对。
2. `PUT /files/{id}/rename` + 目录 rename（支撑 Phase 5 目录治理）。
3. **用户级活动流查询端点**：按 audit_logs 过滤当前 user + resource_type='files'（含 path 解析出文件名）。
4. 统计聚合端点（四卡口径统一由后端定义，消 A5 长期债）。
5. `GET /files` 补 offset/total 分页（为 P4 铺路）。
6. A11 配额：merge 落账改预占制（init 预占、取消释放），或至少加并发超卖保护。
7. A9：merge 响应返回是否发生改名，前端 toast 提示真实落盘名。

## 5. 不可动红线（继承，新增一条）

原 6 条不变（路由/模块 key、上传三段式协议与 upload store 接口、picker 契约、/tracks/ 策略、sync 静默对账行为、fullscreen meta）。

新增：**秒传修复不得改变 init/chunk/merge 三段式协议的形状**——只在 init 入参与 merge 响应语义上做增量，否则 presigned 路径与断点续传全部受影响。

## 6. 风险与回滚

- **最高风险仍是 Phase 1 之前动架构**——P0 缺陷与架构重构零耦合，必须先独立修复上线。
- A1 修复涉及前后端协议增量：先上后端（新参兼容旧前端），再上前端，可灰度。
- A2 序号防竞态在 files store 内实现，回滚 = 回退 store 一个文件。
- 每 Phase 独立 PR，Phase 3 用快照测试锁行为；CI 已有 vitest + vue-tsc 双门禁可直接挂，但**无 lint**，建议顺手补最简 eslint 配置（只开 recommended，不追风格债）。
