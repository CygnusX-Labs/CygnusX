## 4. Phase 2｜目录治理（核心收益期）

### 4.1 一次性清理（DB 操作，先做备份）

**前置备份（必做）**：导出 root 用户（cb79a200）的 `user_directories`、`file_records`、`upload_sessions`、`report_files` 相关行。

**执行顺序（先改引用、再删记录、最后动物理）：**

```sql
-- ① raw-data 实体归位（唯一有真实文件的乱目录）：
-- 物理：mv /data/omichub/users/{uid}/inbox/raw-data/integration_harmony.qs → /data/omichub/users/{uid}/raw_data/
UPDATE file_records SET directory='raw_data' WHERE user_id='{uid}' AND directory='raw-data';
UPDATE upload_sessions SET directory='raw_data' WHERE user_id='{uid}' AND directory='raw-data';

-- ② 删除幽灵目录记录（仅 root 用户；is_system=0 且已核实零物理、零活动引用）
DELETE FROM user_directories WHERE user_id='{uid}' AND (
  path LIKE 'enrichment%' OR          -- 21 条，file_records 0
  path LIKE 'results%' OR             -- 4 条 + 6 条 report_files 死链（③ 处理）
  path = 'raw' OR path LIKE 'raw/%' OR-- 2 条
  path = 'raw-data' OR                -- 根级幽灵
  path LIKE 'raw_data/raw-data%' OR   -- 7 条历史下载登记，物理空
  path = 'inbox/raw-data' OR path LIKE 'inbox/projects%'  -- 孤儿物理节点（Q7）
);
-- 注：执行 ① 后 raw_data/raw-data* 与 inbox/raw-data 的物理对应关系已消失，可安全删除；
--     inbox/projects 为空目录树的孤儿记录（Q7），一并删除。

-- ③ report_files 死链（物理已删的 results/studio 报告附件）：
DELETE FROM report_files WHERE user_id='{uid}' AND path LIKE '%/results/studio/%';  -- 6 条
```

**安全护栏**：所有 DELETE 先以 SELECT 同条件输出条数核对（已知：enrichment 21 + results 4 + raw 2 + raw-data 根级 1 + raw_data/raw-data 7 + report_files 6；`inbox/raw-data` 与 `inbox/projects%` 的条数以 SELECT 实数为准）；单事务执行；`is_system=1` 的记录一律不碰。

### 4.2 堵复发口（机制修复，三条）

1. **sync 反向对账（根治幽灵目录机制）**：`sync_user_files`（file_service.py:904-1004）增加反向 pass——遍历 `user_directories` 现有记录，物理对应路径不存在且解析不到任何候选位置（user_root/{path} 与 inbox/{path} 均不存在）的记录予以删除。护栏：`is_system=1` 不删；有 active `file_records` 子级的目录不删；skip 名单语义不变。这是本方案**最重要的一条机制修复**——不做的话幽灵目录还会再长。
2. **DownloadsView.vue:131**：删除 `targetDirectoryOptions` 里的 `raw-data` 硬编码选项（保留系统目录选项 + 任意目录输入）。复查 `frontend/` 与 `data/ai/prompts/**` 中是否还有其他硬编码目录名选项。
3. **workspace 沙盒残留**：sync skip 名单加 `*.cache`/`zsh.*`/`init.*.zsh` 模式（或沙盒容器 `/workspace` 挂载改 tmpfs 覆盖层）；顺手删除现有 4 个残留文件及对应 4 条 file_records（34KB）。

### 4.3 目录树展示优化（前后端小改，决策点 D1–D3 默认建议已附）

| 项 | 改动 | 效果 |
|---|---|---|
| D1 chat-output 折叠（默认：**做**） | 后端 `list_directories` 把 `workspace/chat-output/{session}` 子树折叠为单个聚合节点「AI 会话产物」（只读、不可在其中新建）；前端 DirectoryTree 按标记渲染为单节点 | 消灭 29 个 UUID 目录的视觉污染；文件仍经消息卡片下载 |
| D2 inbox 隐藏（默认：**做**） | 前端树过滤不渲染 `inbox` 节点（文件按逻辑 directory 显示不受影响，Q7 已验证）；配合 4.1 的孤儿记录清理 | 用户不再看到上传暂存层 |
| D3 tasks 处置（默认：**树中隐藏 + 物理保留只读**） | 前端树过滤 `tasks` 节点（物理与 DB 不动，blast 读取兼容不受影响）；DB 记录加标记或前端硬过滤二选一，建议前端过滤（不动表结构） | 历史任务产物保留可追溯，界面干净 |

前端过滤实现位置：`DirectoryTree.vue:22-23` 的渲染处（当前全量渲染），加过滤谓词；过滤名单（`inbox`、`tasks`、chat-output 展开）从后端返回的目录元数据（is_system + 新增 `visibility` 字段）驱动，不硬编码在前端。

验收：清理后 root 用户目录树 = 6 个系统目录（inbox 隐藏后 5 个可见）+ 用户自建目录；再手动删除任一物理目录后点「同步」，其 DB 记录消失（反向对账生效）；数据下载页不再出现 raw-data 选项。

## 5. Phase 3｜防复发机制（0.5 天）

1. **CI 守卫**：`src/` 禁止 `/data/` 字面量绝对路径（白名单除外），违规即挂。
2. **配置 fail-fast**：`scripts/render_worker_config.py` 渲染时校验 `shared_data_dir` 与 `STORAGE_PATH` 一致，不一致拒绝渲染；`worker_config.yaml` 的 `shared_data_dir` 改为派生值并加注释"由渲染脚本生成，勿手改"。
3. **路径工厂登记**：`path_factory.py` 确认/新增为业务目录唯一构造入口（现状已是事实入口，补文档注释与调用点清单）。

## 8. 红线与禁止事项（实施全程遵守）

1. 不动物理 tasks/ 目录（tasks.work_dir 绝对路径历史账本 + blast 读取兼容）。
2. 不动上传三段式协议、upload store 接口、`GET /files/picker` 契约、`/tracks/` URL 策略、`GET /files/sync` 进页静默对账行为。
3. 不动 MODULE_LOCKED 模块 key 与 `/files` 路由。
4. DB 清理必须备份在先、SELECT 核对条数、单事务；禁止无 WHERE 全表操作。
5. 协作室前缀（`output/agentteams/`、`workspace/agentteams/`）一律不动——等 Gap 3 裁决。
6. 实施顺序纪律：先 Phase 0 门禁（G-A），后修复；先改引用后删记录；每 Phase 独立提交。
