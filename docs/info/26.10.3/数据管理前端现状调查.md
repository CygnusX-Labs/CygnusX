## 2. 前端架构现状

### 2.1 总体结构（关键结论：无 store、无 API 层）

```

├── components/
│   ├── DirectoryTree.vue               ← 374 行，目录树（注意：在 components/ 根目录，不在 data-management/ 下）
│   ├── FilePickerModal.vue             ← 244 行，供 FlowSubmit/FastqQC 选文件
│   ├── ChunkUploader.vue               ← 258 行，上传弹窗（挂在 DefaultLayout，全局）
```

**核心问题：数据管理域没有任何专属 Pinia store，也没有 `src/api/files.ts`。** 所有 REST 调用以 `apiClient.get('/files/...')` 字符串形式散落在 FilesView / DirectoryTree / FilePreviewModal / FilePickerModal 等组件内——违反项目规范「API 调用集中在 `src/api/`」。状态全部是 FilesView 内的本地 ref，无法跨组件复用（DirectoryTree 因此自己再拉一次 `/files/directories`）。

### 2.2 FilesView.vue 内部解剖

页面形态：顶部统计带 + Finder 三栏（左目录树 / 中工作区 / 右详情），移动/平板降级为抽屉。

**数据获取（`fetchAll`，FilesView.vue:62-85）**：一次 `Promise.all` 拉 5 个端点：

| 端点 | 存入 |
|---|---|
| `GET /files` | `allFiles`（全量文件） |
| `GET /files/directories` | `directories` |
| `GET /files/samples` | `samplesCount`（只取 total） |
| `GET /files/quota` | `quota` |
| `GET /teams` | `teams` |

**全部为全量拉取 + 前端过滤**：`spaceFiles`（个人按 directory 过滤 / 团队按 `owner_scope + team_id` 过滤）→ `displayFiles`（搜索 + 排序）全部是 computed 链。后端明明支持 `GET /files?q=` 递归搜索与 `?directory=` 服务端过滤（见 §3），前端完全没用——`allFiles` 无上限，文件量增长后首屏与 computed 都会劣化。

**双空间切换**：`activeSpace: 'personal' | 'team'`，团队空间用 NSelect 选团队，写权限按 `TeamInfo.role`（owner/writer/reader）在 `rowActionOptions` 里做前端按钮级控制（后端有真正的 `_team_role` 鉴权兜底，见 `file_service.py:230-264`）。

**文件操作**：

| 操作 | 实现 | 备注 |
|---|---|---|
| 预览 | `FilePreviewModal` | 按扩展名判定 image/text，文本走 Monaco（复用 `StudioMonacoEditor`），25MB 上限 |
| 下载 | `GET /files/{id}/download` blob + a.click | 前端整文件下载 |
| 移动 | `PUT /files/{id}/move` | dialog 内嵌 NSelect；打开时**再拉一次** `/files/directories`（fetchAll 已有，重复请求） |
| 删除 | `DELETE /files/{id}` | dialog.error 确认 |
| 重命名 | `message.info('重命名功能即将上线')` | **占位假功能**，后端也无端点 |
| 同步 | `POST /files/sync` | onMounted 静默自动对账一次；手动点击弹结果提示 |

**上传**：`uploadStore.open(currentDirectory)` 打开全局弹窗；空状态的 NUpload 拖拽也走同一 store；`watch(completedSeq)` 完成后刷新。上传目标目录固定为「当前目录」，**团队空间下上传/新建/同步按钮全部 disabled**（团队文件只能看和下载）。

**假功能占位清单**（重构时需决策：实现 or 删除）：
- 文件重命名、目录重命名（`DirectoryTree.renameDirectory`）
- 从 SRA / GEO / URL 导入（`importFromSRA/GEO/URL`）
- 「管理存储」面板（StorageOverviewWidget 的 manage-storage 事件 → `message.info('即将上线')`）
- 「清理缓存」实际只是重新 fetchAll
- 帮助文档链接

**响应式**：手写 `updateViewport` + window resize 监听，`<768` mobile、`768-1200` tablet。桌面左右栏与两个 NDrawer（目录抽屉/详情抽屉）之间**模板大面积复制**：space-tabs、DirectoryTree/team-selector、FileDetailPanel+StorageOverviewWidget+RecentActivitiesWidget 组合，桌面侧栏和移动抽屉各写一遍（FilesView.vue:476-512 vs 836-868、796-816 vs 888-909）。

**其他债务**：
- `TYPE_META`/`renderFileTypeTag`（文件类型→Tag 颜色映射）在 FilesView 与 FileDetailPanel 各定义一份；`formatSize` 在 FilesView / OverviewStats / StorageOverviewWidget / FileDetailPanel **四处重复**。
- `fileEmoji()`（后缀→emoji）与 `fileTypeTagMeta`、JBrowseLinkGenerator 的 `bioType()` 三套并存的类型识别逻辑，口径不一致（emoji 只认 zip/tsv/csv/fastq/log）。
- CSS 变量混用 `--arco-primary`/`--arco-primary-light`（Arco Design 时代遗留命名）与 `--neutral-*` 新令牌体系。
- 空状态 SVG DNA 插画 ~60 行内联在模板里。
- 网格视图 `fileIcon()` 恒返回 `ScanOutline`，图标无类型区分。

### 2.3 DirectoryTree.vue

- 自含数据源：`onMounted` 自拉 `GET /files/directories`（与 FilesView 的 directories 各一份，**无共享**）；扁平列表前端组装树。
- 选中态通过 `v-model`（path 字符串，`''`=根）双向绑定父级；目录操作：新建（dialog + `document.getElementById('__dir_name_input')` **DOM hack 取输入值**）、删除（`DELETE /files/directories?path=`，删除当前目录或其祖先时回退根目录）、右键上下文菜单（NDropdown 手动 x/y 定位）+ 悬浮内联按钮两套操作入口。
- 系统目录（`is_system`）灰图标、禁删，但节点可见。
- `defineExpose({ refresh, openCreateModal })` 供 FilesView 调用（工具栏「新建文件夹」按钮经 ref 调子组件方法——父子通信方式偏 hack）。

### 2.4 上传体系（本域最成熟的部分）

三层结构，职责清晰：

1. **`stores/upload.ts`（Pinia）**：跨页面持久队列。`queue / modalOpen / minimized / targetDirectory / completedSeq`；`completedSeq` 自增计数器是 FilesView 的刷新信号。有活跃任务时 close 自动转 minimize。
2. **`composables/useChunkUpload.ts`（引擎）**：
   - 5 MiB 分片，MD5（SparkMD5）三级采样（≤6MiB 全量 / 大文件首+中+尾各 2MiB）用于秒传判定；
   - init → 并发 chunk（并发度 3，分片级 MD5 校验）→ merge 三段式；
   - 断点续传（init 返回 `uploaded_chunks` 跳过已传）、暂停（abort 在途请求）/恢复（重新 init）/取消（`DELETE /files/upload/{upload_id}`）；
   - 429/5xx 指数退避重试（0.5s→4s + 抖动，上限 4 次）；
   - ≥100 MiB 且后端 `presigned_url_enabled` 时优先走 `usePresignedUpload` S3 预签名直传，失败回退分块；
   - merge 请求单独 10 分钟超时（普通 API 30s）。
3. **展示层**：`ChunkUploader.vue`（弹窗）+ `UploadFloatingBall.vue`（最小化悬浮球），都挂在 `DefaultLayout.vue:975-977`，全局常驻、切页不断。

`UploadQueueItem` 状态机：`pending → uploading → merging → completed`，可 `paused / failed / cancelled`（类型定义在 `types/index.ts:184-194`）。

**重构时上传体系建议保持原样**（它是被 DefaultLayout 全局挂载的横切能力，与 FilesView 只是弱耦合：open + completedSeq）。

### 2.5 FilePreviewModal / JBrowseLinkGenerator / 右栏三件套

- `FilePreviewModal`：纯 props 驱动，无状态污染，质量较好；扩展名白名单（图片 8 种、文本 30 种）+ 语言映射硬编码在组件内；文本预览前 1KB 检测 ` ` 防二进制误读。
- `JBrowseLinkGenerator`：生成 `${origin}/tracks/${file.path}` 直链（nginx `/tracks/` alias 到 `/data/cygnusx/`，无鉴权 + CORS + Range，外部 JBrowse 可流式读）。含 .bai/.tbi 索引防呆提示。注意 `/tracks/` 无鉴权依赖 IP 白名单（记忆库 jbrowse2-integration 已登记）。
- 右栏三件套（StorageOverviewWidget / RecentActivitiesWidget / FileDetailPanel）：「近期活跃」**不是真实审计流**，是从 files/directories 的 created_at 前端推导的近似时间线，仅 8 条。

## 3. 后端契约（重构边界参考）

`src/cygnusx/api/v1/files.py`（595 行）→ `application/services/file_service.py`（1104 行）。FilesView 实际消费的端点（加粗）：

| 端点 | 方法 | 说明 |
|---|---|---|
| **`/files`** | GET | **`?directory=`（服务端按目录过滤）/ `?source=` / `?q=`（递归搜索，limit≤200）/ `?limit`**。前端目前只用无参形态 |
| `/files/search` | GET | deprecated（`?q=` 已并入 `/files`） |
| `/files/workspace` | GET | deprecated（MCP/Agent 内部用） |
| `/files/tree` | GET | 文件树（前端未用） |
| **`/files/quota`** | GET | 配额 |
| `/files/storage-info` | GET | 存储模式（预签名开关） |
| `/files/preview` | GET | 内容预览（FilePreviewModal 没用它，直接整文件 blob 下载再渲染） |
| **`/files/sync`** | POST | 磁盘 ↔ file_records 对账 |
| `/files/presigned-download`、`/files/presigned-upload(-complete)` | GET/POST | 云存储模式 |
| **`/files/directories`** | GET/POST/DELETE | 列表/创建/删除（无 PUT 重命名） |
| `/files/picker` | GET | FilePickerModal 专用 |
| **`/files/{id}/move`** | PUT | 移动 |
| **`/files/upload/init` / `chunk` / `merge`**、`DELETE /upload/{upload_id}` | POST/DELETE | 分块上传三段式 + 取消 |
| `/files/chat-upload`（GET/POST） | — | AI 聊天附件（独立链路） |
| **`/files/{id}/download`** | GET | 下载 |
| **`/files/{id}`** | DELETE | 删除 |
| **`/files/samples`** | GET/POST | 样本列表（FilesView 只用 GET 取 total） |
| `/teams` | GET | 来自 `teams.py`，带当前用户 role |

契约缺口（前端假功能的根源）：
1. **无文件/目录重命名端点**——前端两处「即将上线」都在等它。
2. `GET /files` 无 offset/total 分页语义（list 模式整目录返回；q 模式 limit 封顶 200）。
3. 团队文件无独立列表参数，靠 `owner_scope/team_id` 字段由前端过滤。

## 4. 债务清单与风险点（按重构优先级）

### P0 结构性
1. **巨石组件**：FilesView 1296 行，数据获取/状态/布局/操作/样式全在一文件；无专属 store、无 API 层，REST 字符串散落 4+ 个文件。
2. **全量拉取 + 前端过滤**：`allFiles` 无上限；后端已具备 `?directory=` / `?q=` 能力但闲置。数据量增长后是确定性性能瓶颈。
3. **状态双份**：directories 在 FilesView 与 DirectoryTree 各拉一份；move 弹窗第三次拉取。切目录/上传后靠整页 fetchAll 粗粒度刷新。

### P1 代码质量
4. 死代码：`DataTypesWidget.vue`、`QuickActionsWidget.vue` 零引用；`JbrowseFileDrawer` 放错目录（唯一消费者在 BioTools）。
5. 重复逻辑：`formatSize` ×4、`TYPE_META` ×2、三套文件类型识别（emoji/Tag/bioType）。
6. 桌面/移动模板复制（三栏 vs 双抽屉整段重复）。
7. `DirectoryTree` 的 `document.getElementById` 取输入值、FilesView 经 ref 调子组件 `openCreateModal`——父子通信 hack。
8. CSS 变量 `--arco-*` 遗留与新令牌混用。

### P2 产品完整性
9. 假功能占位：文件/目录重命名、SRA/GEO/URL 导入、管理存储、帮助文档（后端多数也无对应端点）。
10. 团队空间只读体验（上传/新建/同步禁用），且团队文件列表靠前端过滤。
11. 预览未用 `/files/preview` 端点，而是整文件下载后前端判断（大文本文件白白传输；25MB 上限是补偿）。

### 测试现状
**该域前端测试覆盖为零**：`views/__tests__/`、`stores/__tests__/` 无 FilesView/upload 相关用例（上传引擎 useChunkUpload 的重试/断点逻辑完全无回归保护）。重构前建议先给 upload store + 关键 computed 补快照/单测再动手。

### 不可动的边界（重构红线）
- 路由 path `/files`、模块 key `files`（MODULE_LOCKED 双端消费）。
- 上传三段式协议与 upload store 对外接口（DefaultLayout 全局挂载）。
- `GET /files/picker` 契约（FlowSubmit/FastqQC 依赖）。
- `/tracks/` 直链 URL 策略（外部 JBrowse 兼容）。
- `GET /files/sync` 进页静默对账行为（磁盘与 DB 一致性依赖，见记忆库 download-files-need-db-registration）。

## 5. 重构方向建议（供下一步讨论）

1. **建 `src/api/files.ts`**：集中 files/directories/samples/quota/teams/upload 全部调用与响应类型（对齐 `api/projects.ts` 等既有模式）。
2. **建 `stores/files.ts`**（或 `fileExplorer.ts`）：持有 files/directories/quota/teams/space/directory 状态 + fetch 变体（按目录增量、搜索走 `?q=`），DirectoryTree 与右栏组件全部改为消费 store，消灭双份拉取。
3. **FilesView 拆分**：`FilesToolbar` / `FileBreadcrumb` / `FileTable` / `FileGrid` / `SpaceSwitcher`（含移动抽屉合一——用同一组件树 + 响应式容器切换，消除模板复制）。
4. **工具函数下沉**：`formatSize` → `utils/format.ts`；`TYPE_META`/类型识别 → 单一 `utils/fileType.ts`，emoji/Tag/badge 三视图共用一个数据源。
5. **服务端过滤迁移**：切目录改走 `?directory=`、搜索框防抖后走 `?q=` 递归搜索（顺带获得跨目录搜索能力），`allFiles` 全量仅保留给统计/活跃推导（或统计也走后端）。
6. **假功能决策**：重命名需先补后端端点（文件+目录各一），SRA/GEO 导入若近期不做建议先撤按钮，避免重构搬运占位代码。
7. **清理**：删 DataTypesWidget/QuickActionsWidget，JbrowseFileDrawer 迁至 `components/bio-tools/` 或 jbrowse 相关目录。
8. DirectoryTree 新建弹窗改受控表单组件，去 getElementById。

估算涉及面：前端约 10 个文件改动 + 2 个删除；后端可选新增 rename 端点（须带 Alembic 无关、仅 service+route，走 ruff/mypy/pytest 门禁）。
