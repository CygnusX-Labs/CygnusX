## 一、五个目录的创建来源（核心）

### 总体事实（影响所有结论）

**目录树的数据源是 `user_directories` 表（DB），不是物理磁盘**。`GET /files/directories` → `DirectoryService.list_directories()`（`directory_service.py:124`）直接返回 `user_directories` 表全部记录。前端 `DirectoryTree.vue:22-23` 明确注释「不再按硬编码白名单隐藏文件夹，所有目录树节点均可见」，把表里所有记录（含幽灵目录）全部渲染。

五个幽灵/实体目录**只出现在 root 用户（cb79a200）一人**的 `user_directories` 里：

```
SELECT path, is_system, created_at FROM user_directories
WHERE user_id='cb79a200-...' AND path IN ('enrichment','results','tasks','raw','raw-data');
→ enrichment | f | 2026-07-19 19:26
→ raw        | f | 2026-08-03 09:03
→ raw-data   | f | 2026-08-03 02:08
→ results    | f | 2026-07-18 03:20
→ tasks      | f | 2026-07-28 05:55
```

其余 7 个用户（admin/demo/agentteams_bridge 等）的表里只有 6 个系统目录，无任何杂项目录。

**物理磁盘核查（root 用户根目录 `ls -la` 实测）**：实际只有 7 个目录——downloads / inbox / projects / raw_data / **tasks** / temp / workspace。`enrichment`、`results`、`raw`、`raw-data` 四个目录**物理不存在**，也没有软链（`find -maxdepth 2 -type l` 为空）。

### Q6：POST /files/sync 对账逻辑

**会**。`sync_user_files`（file_service.py:904-1004）先扫描磁盘所有目录，凡不在 skip 名单（tasks/projects/temp/results/raw 顶层 + workspace/chat-uploads、workspace/sandbox + 隐藏目录）的，逐级 `ensure_directory_chain` 登记（:950-958）；再登记文件（:960-993），同 storage_path 幂等跳过，active 记录物理消失则删除（:929-934）。
**所以用户手动 scp 进 raw_data/downloads/inbox 子目录的文件，下次 sync 后会自动出现在树里**（这正是 `projects/variant/PRJNA1285930` 37GB .sra 文件的入库方式——directory 字段为空、显示在根目录视图，但 storage_path 在 projects/variant 下，说明是 09-25 手动 scp 后 sync 登记的）。
**对账方向**：磁盘有 → DB 补；磁盘无 → DB 删（仅 active 记录）。**但 user_directories 表没有反向清理**——这就是 4 个幽灵目录至今残留的机制性原因：物理目录删了，file_records 被 sync 清了，**user_directories 记录永远不会被 sync 删除**（sync 只增不减该表）。

## 三、系统目录可见性决策素材

### Q7：inbox 层级

- **结构**：`inbox/` 下现有 `raw-data/`（1 个 212MB .qs 文件）和 `projects/`（空目录树，用户曾以 "projects/sctna-seq-test" 为上传目录路径）。**inbox 根下无散文件**。
- **directory 字段写什么**：上传时写的是**用户视角的逻辑目录**（如 `raw-data`、`projects/sctna-seq-test`），物理路径在 inbox/ 下。`_derive_directory`（file_service.py:1007）统一剥 inbox/ 前缀——即 **inbox 本身永远不出现在 file_records.directory 里**，inbox 根上传 → directory=''（根目录视图）。
- **若隐藏 inbox**：上传文件不断——用户在根目录视图（directory=''）看到的 inbox 根上传文件、在 `raw-data` 节点看到的子目录文件都不依赖 inbox 节点本身。断点只有两处：a) DirectoryTree 显示的 `inbox/raw-data`、`inbox/projects/sctna-seq-test` 这类**物理真实但逻辑剥离后的孤儿节点**（DB 有 inbox/raw-data 条目，文件显示在逻辑 raw-data 节点下，两处显示会分叉）；b) 用户在 inbox 节点下「新建子目录」的操作路径。**建议**：隐藏 inbox 节点 + 删掉 `inbox/raw-data`、`inbox/projects` 这两条 DB 记录（文件按逻辑 directory 显示不受影响）。

### Q8：temp

- **内容**：物理空（4.0KB，mtime 2026-07-25）。
- **配置**：`file_temp_retention_days=30`（config.py:226），`.env` 无覆盖（默认值生效）。
- **清理任务在跑吗**：beat 已登记 `cleanup-expired-archives`（celery.py:116，每日 02:00 → `storage.cleanup_expired`），worker 已加载该 task。**但无法从现有日志确认最近一次实际执行**——beat 今天 14:24 才重启（docker inspect），日志窗口内只有 5s 级周期任务；且 `file_records` 中 status='temp'/'uploading' 的记录数为 0，cleanup 即使跑了也无事可做。temp/ 物理为空与该任务行为一致（它只删 FileRecord 标记的临时文件，不扫目录）。**[待人工确认]**：想确认执行证据需明天 02:00 后查 `docker logs cygnusx-worker | grep cleanup_expired`。

### Q9：workspace

- **结构**：`workspace/` 顶层 = `chat-output/`（29 个会话目录，20MB）+ `chat-uploads/`（34 个文件）+ **4 个沙盒 shell 残留文件**：`init.8920918874217841234.zsh`、`omp.cache`、`zsh.{两个uuid}.omp.cache`（07-27~08-05 mtime）。
- **Studio 沙盒会漏吗**：**不会**。Studio 沙盒工作区在 `/data/omichub/studio/{session_id}`（tasks 表 studio_sandbox 任务 work_dir 实证），完全独立于 workspace/。chat 沙盒产物也只写 `workspace/chat-output/{session}/output/`（chat_sandbox_tools.py:237），不会散落。**唯一漏点就是那 4 个 zsh/omp 缓存文件**——疑似 chat 沙盒容器把 shell 初始化缓存写到了挂载的 workspace 根（`/workspace` 挂 workspace 目录）。它们会躲过 sync 清理（非隐藏目录、workspace 根文件允许登记——file_records 里 directory='workspace' 的 4 条 34KB 记录就是它们）。建议清理 + 在 sync skip 里加 `*.cache`/`zsh.*` 模式或沙盒容器改为 tmpfs。
- **workspace/chat-output 值得注意**：29 个会话目录全部按 `directory='workspace/chat-output/{uuid}/output'` 登记 file_records（source='chat_sandbox'），目录树里 workspace 下挂 29 个 UUID 目录——**这是现在目录树最大的视觉污染源**（比 5 个幽灵目录多得多）。
