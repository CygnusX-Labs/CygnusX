# CygnusX BioOps · 可复现分析报告功能设计框架

> 版本：v0.1（讨论稿）
> 日期：2026-10-12
> 定位：核心交付物功能设计，支撑"可信科研交付"定位

---

## 一、功能定位与核心价值

### 1.1 为什么要做这个功能

当前平台的核心能力（证据胶囊、环境快照、三级质量门、产物指纹）都在后台运行，用户**感知不到**。

一键导出的可复现报告，是把这些后台能力**可视化、可交付、可归档**的最直观载体。用户拿到这份报告的那一刻，才会真正理解"可信科研交付"是什么意思。

### 1.2 核心价值主张

> **"每一次分析，都自动生成可复现报告——包含环境快照、参数记录、质量门结果、产物指纹和一键重跑入口。让每一次科研计算，都经得起时间和同行的检验。"**

### 1.3 解决的用户痛点

| 场景 | 传统方式的痛苦 | 报告解决的问题 |
|---|---|---|
| 人员交接 | 翻聊天记录、找脚本、猜参数，以周计 | 一份报告 10 分钟完成交接 |
| 论文方法部分 | 手工整理工具版本、参数、流程 | 直接从报告复制方法描述 |
| 客户交付 | 黑盒结果，客户不信任 | 完整过程透明，可审计 |
| 内部审计 | 不知道分析怎么做出来的 | 报告就是审计凭证 |
| 论文返修 | Reviewer 问参数，翻代码翻半天 | 报告里全有 |

## 二、报告整体结构（八大模块）

### 模块 1：封面与概要

- 项目名称、分析目标、生成时间
- 分析负责人、执行 Agent 版本号
- 一句话总结：本次分析做了什么、核心结论
- **复现声明**：本报告中所有结果，均可在相同环境下一键复现
- 平台 Logo + 报告生成日期

### 模块 2：输入与环境信息

**2.1 输入数据清单**
- 文件名、文件大小、MD5 校验值
- 数据来源（用户上传 / GEO/SRA 拉取 / 其他数据库）
- 样本分组信息（对照组 vs 处理组）

**2.2 计算环境**
- 容器镜像哈希（Docker/Singularity）
- Conda Lockfile 内容摘要
- 操作系统、CPU 核数、内存规格
- 执行队列 / Worker 节点信息

**2.3 模型配置**
- 本次分析调用了哪些大模型
- 每个模型的名称、版本、调用方
- 关键参数：temperature、top_p、max_tokens、随机种子

**2.4 随机种子**
- 所有用到随机数的步骤，seed 值逐一列出
- 包括：模型推理 seed、流程执行 seed、统计分析 seed

### 模块 3：执行轨迹时间线（核心模块）

按时间顺序，逐步列出分析过程：

```
Step 1: 数据导入与质控
  ├─ 开始时间：10:23:15
  ├─ 结束时间：10:24:00
  ├─ 耗时：45 秒
  ├─ 执行方：领域 Agent（RNA-seq Analyst v1.2）
  ├─ 调用 Skill：FASTQ 质控（v1.2.0）
  ├─ 输入：sample_R1.fastq.gz, sample_R2.fastq.gz
  ├─ 参数：线程数=8, 最小质量分=20
  ├─ 输出：fastqc_report.html,质控摘要.json
  ├─ 状态：✅ 成功
  └─ 备注：Q30 = 92.3%，达标

Step 2: 序列比对
  ├─ ...
  └─ 状态：✅ 成功

Step 3: 定量与差异分析
  ├─ ...
  └─ 状态：⚠️ 警告（Q30 略低于阈值 85%，实际 82%）
```

每一步必须包含：
- 谁做的（Agent / Skill / 人工）
- 用了什么工具（名称 + 版本）
- 什么参数
- 输入是什么
- 输出是什么
- 花了多久
- 成功没有 / 有没有警告

### 模块 4：API 与外部工具调用清单

- 本次分析一共调用了哪些外部服务 / API
- 每个 API 的：名称、调用时间、请求参数摘要、返回状态码
- 调用了哪些 MCP 工具，版本号是多少
- 有没有数据出境（访问外部数据库）

**价值**：审计合规。药企和合规客户要的就是这个——这次分析到底连了什么外网。

### 模块 5：质量门结果

- **一级预检**：格式校验、样本表校验、参考基因组路径校验——通过 / 不通过，具体指标值
- **二级运行中 QC**：每一步的关键质控指标（Q30、Mapping Rate、Multi-Mapping Rate、TSS/FRiP 等），和阈值对比
- **三级统计审核**：FDR 校正、异常值检测、Cook's Distance 离群点分析结果

把 QC 结果放进报告 = 告诉用户：这个结果不是 AI 拍脑袋给你的，是过了三道质量门的。

### 模块 6：产物与交付物清单

- 所有输出文件：文件名、大小、MD5 校验值
- 关键图表：火山图、热图、PCA 图——直接嵌入报告
- 中间产物 vs 最终产物分类
- 文件在项目空间中的路径

### 模块 7：证据链与因果关系图

- 用 Mermaid / D3.js 画流程图：从输入数据 → 每一步处理 → 最终结果
- 遵循 W3C PROV 标准的因果关系
- 哪个输入产生了哪个中间产物，哪个 Skill 生成了哪个文件
- 一眼看懂整个分析的来龙去脉

### 模块 8：一键复现指南

- **怎么重跑**：一条命令 / 一个按钮
- **需要什么环境**：镜像已经打包好了，直接拉起
- **预期结果**：应该得到和本次相同的产物 MD5
- **复现验证**：一键重跑后自动对比产物指纹，一致则标记"复现成功"

这是整个报告的灵魂。你卖的不是"分析结果"，是"可复现的分析结果"。

## 四、技术实现方案

### 4.1 整体架构

```
[各数据源] → [ReportBuilder 聚合层] → [Jinja2 模板渲染] → [HTML 报告]
                                                          ↓
                                                    [Playwright 转 PDF]
```

### 4.2 核心模块

**1. ReportBuilder（数据聚合层）**
- 输入：项目 ID / 分析任务 ID
- 从各个数据源拉取结构化数据
- 组装成 ReportData 对象
- 做数据完整性校验（缺字段就标红警告）

**2. ReportTemplate（渲染层）**
- Jinja2 HTML 模板
- 支持折叠、展开、锚点跳转
- 图表内嵌（base64 或者 URL）
- 响应式布局，打印友好

**3. PDFExporter（导出层）**
- Playwright headless Chromium 打印 PDF
- 支持自定义页眉页脚
- 报告水印（项目名 + 用户 + 日期）

**4. ReportController（API 层）**
- 接口：`GET /api/projects/{id}/reports/{task_id}/export?format=html|pdf`
- 异步生成：大报告后台生成，完成后通知
- 权限：只有项目成员可以导出

### 4.3 开发量估算

| 阶段 | 内容 | 预估工时 |
|---|---|---|
| Phase 1 | ReportBuilder 聚合层 + HTML 基础模板 | 1 周 |
| Phase 2 | 八大模块内容填充 + 样式打磨 | 1 周 |
| Phase 3 | PDF 导出 + 一键重跑入口 | 3-5 天 |
| Phase 4 | 证据链可视化（Mermaid） | 2-3 天 |
| **合计** | | **约 2.5–3 周** |

## 五、迭代优先级

| 优先级 | 功能 | 说明 |
|---|---|---|
| **P0** | HTML 版完整报告 | 先做 HTML，交互性好，开发快 |
| **P1** | PDF 导出 | Playwright 转 PDF，技术成熟 |
| **P2** | 证据链流程图（Mermaid） | 先做简单版，不用上 D3.js |
| **P3** | 一键重跑按钮 | 报告里直接点一下就重跑 |
| **P4** | 报告对比功能 | 两次分析的报告 diff |
| **P5** | 自定义报告模板 | 用户可以选哪些模块要 / 不要 |

## 六、商业价值与应用场景

### 6.1 直接商业价值

- **药企客户**：报告直接进实验记录系统，节省人工整理时间
- **高校课题组**：学生交接、论文方法部分，省大量沟通成本
- **第三方检测机构**：交付给客户的标准化报告，提高专业度

### 6.2 间接品牌价值

- README 里可以直接放报告样例，比任何架构图都有说服力
- 客户演示时，一键导出报告 = 直观展示"我们是可信的"
- 论文/博客案例，报告就是最好的证据

### 6.3 对产品定位的强化

报告是"可信交付"这个定位的**实体化载体**。没有报告，"可信"是个概念；有了报告，"可信"是一个用户拿在手里的 PDF。

## 七、今晚需要想清楚的问题清单

### 7.1 报告内容层面

- [ ] 八大模块，哪些是必须的？哪些是可选的？
- [ ] 报告的详细程度——是"完整审计级"还是"摘要交付级"？要不要做两种粒度？
- [ ] 图表要不要内嵌？内嵌的话图片大小怎么控制？
- [ ] 用户能不能自定义报告内容？比如只要结果不要过程？

### 7.2 交互层面

- [ ] 报告在哪里导出？项目页？分析详情页？聊天窗口？
- [ ] 报告生成是实时的还是异步的？大报告要多久？
- [ ] 报告能不能分享？外部链接？权限控制？
- [ ] 历史报告怎么管理？每个分析任务一份？还是按项目汇总？

### 7.3 技术层面

- [ ] ReportBuilder 从哪里拉数据？直连数据库？还是走事件总线？
- [ ] 模板放在哪里？代码仓库里？还是数据库里？方便后面自定义？
- [ ] PDF 用 Playwright 还是 WeasyPrint？哪个效果好、维护成本低？
- [ ] 报告生成失败怎么办？缓存机制要不要做？

### 7.4 产品层面

- [ ] 报告是免费功能，还是高级功能？云订阅用户才有？
- [ ] 私有化部署的客户，报告样式能不能定制？加客户 Logo？
- [ ] 报告里要不要加"平台水印"？品牌露出？
- [ ] 后续要不要做"报告市场"——用户分享自己的报告模板？

## 八、后续展望

这个功能做出来之后，可以延伸的方向：

1. **报告智能解读**：AI 帮你总结报告里的关键结论
2. **报告对比**：两次分析的结果 diff，看差异在哪里
3. **报告审批流**：报告生成后，需要导师/PI 审批才能交付
4. **报告归档**：按项目自动归档，多年后还能翻出来看
5. **报告 API**：客户系统可以直接调 API 拉报告，做自己的 BI
