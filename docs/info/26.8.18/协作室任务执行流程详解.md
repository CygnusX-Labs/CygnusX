## 1. 总体架构概览

协作室的系统分为三层：

```
┌─────────────────────────────────────────────┐
│           第1层: OmicHub Platform             │
│  FastAPI (Python) + Vue 前端                  │
│  - 消息接收 / 意图路由 / Agent协调            │
│  - 知识库检索 / Domain Rules 匹配             │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│        第2层: AgentTeams Bridge               │
│  Matrix 房间管理 + Case 生命周期              │
│  - 创建工作项 (Work Items)                    │
│  - Worker 招募与调度                          │
│  - 质量门控与审批                              │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│       第3层: Agent Teams Gateway/Workers      │
│  实际 Agent 执行层                            │
│  - agent-rnaseq, agent-viz, agent-code ...   │
│  - RNAFlow Pipeline / Snakemake              │
│  - ggtree / IQ-TREE 工具调用                 │
└─────────────────────────────────────────────┘
```

### 两条编排路径

用户在协作室发起任务后，根据请求类型进入**不同路径**：

| 路径 | 触发条件 | Planner | 特点 |
|------|---------|---------|------|
| **Overdrive / LLM 规划路径** | 通用请求，不在预定义 Flow 中 | LLM (Manager → Lead Planner) | LLM 辅助决策工作项分配，受 domain rules 约束 |
| **Bridge Workflow 路径** | 命中预定义的 `data/ai/flows/*.yaml` | 硬编码 Work Item 创建 | 质量审计 / 交付 / 解读等节点 Target 写死在代码中 |

## 3. 两种分析路径对比

### Overdrive 路径（LLM 辅助规划）

```
用户请求
  │
  ├─→ Domain Registry 匹配 (匹配 message_markers)
  │     data/ai/domains/omics.yaml → rnaseq-domain 规则
  │     data/ai/domains/phylo.yaml → task_type slot
  │
  ├─→ Lead Planner Selector (DOMAIN_HINTS 评分)
  │
  ├─→ Research Phase (知识库 + 网页搜索)
  │
  ├─→ LLM 生成 assignments (受 domain rules 约束)
  │
  └─→ Plan Builder (模板组装 enriched_tasks)
```

### Bridge Workflow 路径（硬编码 Work Items）

```
用户请求命中 preflow
  │
  ├─→ flow YAML 中的 stages/edges 被读取
  │
  ├─→ Bridge service 硬编码创建 work items:
  │     quality-01 → target="quality-auditor"
  │     delivery-01 → target="delivery-reporter"
  │     interpret-01 → target=lookup(interpretation_target)
  │
  └─→ DAG topological sort 决定执行顺序
```

## 4. 场景一：输入"帮我进行rna-seq分析"

### 4.1 关键前置判断——是否有附件？

**文件**: `execution_intent.py:63-80`

系统首先运行 `detect_execution_intent()`，需同时满足三个条件才进入执行模式：

| 条件 | "帮我进行rna-seq分析"(无附件) | "帮我进行rna-seq分析"+FASTQ |
|------|------|------|
| 未命中否决词 | ✅ | ✅ |
| 含执行动词("分析") | ✅ | ✅ |
| 有明确作用对象(context_refs或文件名) | ❌ | ✅ |
| **结果** | **对话式回复（咨询模式）** | **进入执行流程** |

> ⚠️ **纯文本无附件时不会启动任何 Agent**。Manager 会追问数据来源、物种、实验设计等信息。

下面假设你附带了 FASTQ 文件或已上传的数据，进入执行流程。

### 4.2 完整执行步骤

#### Step 1: 消息接入与异步分发

**文件**: `agentteams.py:546-571`

```python
POST /cases/{case_id}/messages
  → 保存为 room.user_message 事件
  → Celery 异步任务: respond_to_room_message.delay(case_id, user_id, content)
```

#### Step 2: Manager 初始回复

**文件**: `room_response_service.py`

1. 获取 Redis 锁（防并发）
2. 获取 case 状态 + 最近 30 条消息
3. 构建 prompt（用户消息 + context_refs + 用户偏好）
4. 选择 Manager agent（优先 `agent-general`）
5. 调用 `AgentConsultationService.run_consultation(capability="interpretation")`

此步只是快速确认收到请求，如果意图检测通过，将触发 `_maybe_start_chat_execution()`。

#### Step 3: 意图路由 → 匹配 RNAFlow

**文件**: `agentteams_intent_router.py`

```python
_EXTRA_HINT_ALIASES = {
    "rnaseq": ("转录组", "差异表达"),
}
```

从 `data/ai/flows/rnaseq.yaml` 读取 trigger_hints：
```yaml
trigger_hints: [RNA-seq, bulk RNA, 差异分析, RNAFlow]
actor: agent-rnaseq
bridge_workflow: rna_seq
```

判定结果: `IntentRoute(flow_id="rnaseq", lead_planner="agent-rnaseq")`

#### Step 4: Domain Registry 匹配

**文件**: `domains/omics.yaml:60-65`

```yaml
assignments:
  rules:
    - id: rnaseq-domain
      when_message_markers: [bulk, rna-seq, 转录组, 表达矩阵]
      agent_match: [agent-rnaseq, rna-seq 分析师]
      task_id: domain-analysis
```

同时 `overdrive_planning_service.py` 的 DOMAIN_HINTS 也会匹配：
```python
"agent-rnaseq": ("rna-seq", "rnaseq", "bulk rna", "转录组", "差异表达", "deseq"),
```

#### Step 5: 研究阶段 (Research Phase)

LLM 收集：
- 平台 RNA-seq 知识库中的最佳实践
- 网络上的最新方法/数据库版本
- 模型通用知识

#### Step 6: Plan 构建与 Case 创建

**文件**: `chat_service.py:3903` / `agentteams_service.py`

Plan Builder 组装 enriched_tasks 并创建 Case Payload：
```python
{
    "case_id": "bioops_<uuid>",
    "intent": "帮我进行rna-seq分析",
    "execution_mode": "cluster_case",
    "flow_id": "rnaseq",
}
```

创建 Matrix 房间并配置参与者。

#### Step 7: Agent 编排执行

##### A. RNAFlow Pipeline 的实际两步 (YAML 定义)

**文件**: `data/ai/flows/rnaseq.yaml:17-41`

```yaml
stages:
  - key: quantify                # Stage 1: 定量与质控
    executors:
      - key: rnaflow
        queue: rnaseq_analysis
        resource_profile: standard_8c32g
        inputs: [fastq_manifest]
        outputs: [quant_counts]

  - key: differential            # Stage 2: 差异表达与审查
    executors:
      - key: deseq2
        queue: rnaseq_analysis
        inputs: [quant_counts]
        outputs: [de_results]
    review:
      skill: de-review
      output: de_review
    gate: {template: annotation_revision, required: true}

edges: [[quantify, differential]]

thresholds:
  mapping_rate: 0.70    # 比对率 ≥ 70%
  q30: 0.80             # Q30 ≥ 80%
  duplicate_rate: 0.50  # 重复率 ≤ 50%
```

##### B. 底层 Snakemake 流水线的真实子步骤

**文件**: `pipelines/RNAFlow/src/src/` 下的脚本

```
MD5 校验 → FastQ Screen(污染筛查) → 文库方向检测
    ↓
RSEM 基因级定量 (STAR+RSEM 或 Salmon准比对)
    ↓
DEG 差异分析 (DESeq2) + 热图/PCA 可视化
    ↓
富集分析 (GO/KEGG/GSEA)
    ↓
可选: rMATS 可变剪接分析
    ↓
HTML 报告生成 + 产物打包交付
```

##### C. Agent Teams 层面的 Agent 参与

由于走的是 workflow-execution 路径，Bridge service 硬编码添加了以下工作项：

| Work Item | Target | 谁执行 | 来源 |
|-----------|--------|--------|------|
| plan-01 | agent-rnaseq | agent-rnaseq | dynamic (Lead Planner) |
| preflight-01 | data-steward | agent-data | hardcoded |
| quality-01 | quality-auditor | agent-qc | hardcoded |
| interpretation-01 | interpretation_target | agent-rnaseq | lookup |
| delivery-01 | delivery-reporter | agent-delivery | hardcoded |

Agent Teams Worker 注册表中可用的人员：

| Agent | 角色 | Skills |
|-------|------|--------|
| **agent-rnaseq** | 主规划者 + RNAFlow 执行专家 | rnaflow, deg, enrichments, wgcna, rmats |
| **agent-data** | 数据预检 | project-preflight, evidence-retrieval |
| **agent-qc** | 质量门控 | quality-gate, artifact-inspect |
| **agent-viz** | 可视化 | visualization-review, figure-specification |
| **agent-code** | 代码生成/调试 | code-review, reproducibility-advice |
| **agent-delivery** | 产物交付 | delivery-pack, runbook-capture |

## 5. 场景二：输入"帮我进行系统发育树和解读"

### 5.1 与 RNA-seq 的核心区别

| 维度 | RNA-seq | 系统发育树 |
|------|---------|-----------|
| 预定义 Flow | `data/ai/flows/rnaseq.yaml` ✅ 存在 | `data/ai/flows/treeplot.yaml` ✅ 存在（但更简单） |
| Domain Rules | `data/ai/domains/omics.yaml` 复杂规则 | `data/ai/domains/phylo.yaml` 带 intake 问答 |
| Slot 分类 | 仅一个 `domain-analysis` 任务 | **两类互斥分支**: `tree_visualization` vs `phylogeny_construction` |
| 强制锚点 | 无 | homolog-search → phylogeny-build 两锚点依赖链 |
| LLM 自由度 | 较低（受 2 stage 限制） | 中等（可拆分/重组 sub-tasks，但锚点不可变） |

### 5.2 意图检测

与 RNA-seq 相同的路径：`detect_execution_intent()` 检查执行动词 + 作用对象。

关键词匹配来自 `data/ai/domains/phylo.yaml` 的 domain_markers：
```yaml
domain_markers:
  - 系统发育
  - 进化树
  - phylogenetic
  - 建树
  - 进化分析
  - 序列比对
  - 同源序列
  - treefile
  - treeplot
  - ggtree
  ...
```

"系统发育"和"建树"都在列表中，Domain Registry 命中 `phylo` 域。

### 5.3 Slot 分类——两种互斥路径

这是系统发育任务的关键分支点：

```
检测到 domain_marker ∈ phylo_markers
         │
    ┌────▼──────────────────────────────────┐
    │ Slot 匹配 task_type                    │
    │                                        │
    │ 命中 markers: [已有树, 美化, treeplot] │ → task_type = tree_visualization
    │ 命中 markers: [建树, 进化分析, 建树]   │ → task_type = phylogeny_construction
    └────┬──────────────────────────────────┘
```

#### 分支 A: tree_visualization（处理已有树）

```yaml
# phylo.yaml:99-104
rules:
  - id: tree-viz-only
    when_slot_is: {task_type: tree_visualization}
    minimize_to_single: true      # 只分配一个 Agent
    agent_match: [agent-viz]
    task_id: tree-visualization
    task: "处理已有系统发育树文件...不要重新建树"
```

**Agent**: 仅 `agent-viz`（最小化到单个 Agent）

#### 分支 B: phylogeny_construction（从头建树）— 你问的场景

这里有 **两个权威锚点（authoritative anchors）**：

```yaml
# phylo.yaml:105-129
rules:
  - id: homolog-search
    when_slot_is: {task_type: phylogeny_construction}
    authoritative: true
    required: true
    allow_split: true             # 可按基因组分片
    allow_reorder: false          # 不可重排
    agent_match: [agent-code]
    task_id: tnpd-homolog-search
    task: "验证 TnpD 查询序列与 20 个基因组输入，逐基因组检索并提取同源候选"

  - id: phylogeny-build
    when_slot_is: {task_type: phylogeny_construction}
    authoritative: true
    required: true
    allow_split: false            # 不可拆分
    allow_reorder: false          # 不可重排
    depends_on: [tnpd-homolog-search]  # ← 硬依赖！
    agent_match: [agent-viz]
    task_id: tnpd-phylogeny
    task: "对筛选后的序列做多序列比对，选择替换模型构建带支持度评估的系统发育树"
```

### 5.5 Branch A vs Branch B 对比

| 维度 | Branch A: 已有树 | Branch B: 从头建树 |
|------|-----------------|-------------------|
| task_type | tree_visualization | phylogeny_construction |
| Agent 数量 | 仅 1 个 (minimize_to_single) | 2 个锚点 + Bridge 附加 |
| Agent 列表 | agent-viz | agent-code → agent-viz → agent-qc/delivery |
| 锚点数 | 0 | 2 (homolog-search + phylogeny-build) |
| 并行性 | N/A | homolog-search 允许 split |
| 依赖链 | 无 | homolog → phylogeny (强依赖) |
| 底层工具 | ggtree / ape | Diamond → MAFFT → IQ-TREE → ggtree |
| 可修改自由度 | 高（仅一个 Agent） | 低（锚点不可动，但 Agent 内可细化） |

## 6. 固定 vs 动态：流程有多大自由度？

### 固定部分 🔒

| 层级 | 具体内容 | 文件位置 |
|------|---------|---------|
| Flow YAML 的阶段数 | RNA-seq 固定 2 stage，TreePlot 固定 1 stage | `data/ai/flows/*.yaml` |
| Bridge Work Item Targets | quality-01 → quality-auditor, delivery-01 → delivery-reporter | `service.py:434-505` |

## 7. 关键判断逻辑——意图检测

**文件**: `execution_intent.py:63-80`

```python
def detect_execution_intent(content: str, context_refs: list[dict]) -> bool:
    """全部满足才返回 True"""
    text = (content or "").strip()
    if not text:
        return False
    # 1. 未命中一票否决词
    if any(p.search(text) for p in _VETO_PATTERNS):
        return False  # "能做什么","介绍一下","是什么","为什么"...
    # 2. 含执行动词
    if not _EXECUTION_VERB_PATTERN.search(text):
        return False  # 需要包含:"分析|运行|执行|跑|可视化|绘图|画"...
    # 3. 有明确作用对象
    if context_refs:
        return True  # 有附件引用 → 直接通过
    return bool(_FILE_NAME_PATTERN.search(text))
    # 或: 文本中包含带扩展名的文件名(.fasta, .fastq, .csv...)
```

这就是同样的话 **"帮我进行rna-seq分析"**，有时触发 Agent 有时不触发的根本原因。
